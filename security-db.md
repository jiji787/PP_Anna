## 1. Ролевая модель

В PostgreSQL созданы три роли:

- **app_user** – для подключения приложения. Имеет права на чтение, вставку, обновление и удаление данных во всех таблицах схемы `public`. Не может создавать или изменять структуру БД.
- **admin_user** – для административных задач. Имеет права суперпользователя (может создавать роли, изменять конфигурацию, делать бэкапы).
- **backup_user** – для резервного копирования. Имеет только право на чтение всех таблиц.

Скрипт создания ролей находится в `deploy/create_roles.sql`. Пароли для ролей хранятся в Vault (или в зашифрованном виде), а не в коде.

## 2. Аудит действий

Для отслеживания доступа к данным рекомендуется включить расширение `pgAudit` или настроить логирование через `log_statement = 'ddl'` и `log_connections = on`. В нашем проекте мы используем стандартные логи PostgreSQL для отслеживания медленных запросов и блокировок (см. `logs/postgresql_log_2026-06-23.txt`).

В будущем можно добавить триггеры, которые записывают изменения критических таблиц (например, `users`) в отдельную таблицу аудита.

## 3. Шифрование

- **Передача данных:** все соединения с БД должны использовать SSL/TLS. В локальной среде мы используем незащищённое соединение (для простоты), но в продакшене обязательно настраивается сертификат.
- **Хранение паролей:** пароли пользователей хранятся в зашифрованном виде (хэш + соль). В нашем приложении пароли не хранятся (нет таблицы с паролями), но если бы они были – использовался бы `bcrypt` или `PBKDF2`.
- **Секреты:** строка подключения к БД и пароли ролей хранятся в Vault (реализован `VaultSecretService`), а не в файлах конфигурации.

## 4. Резервное копирование

Скрипт `deploy/backup_db.bat` создаёт дамп базы данных `Золотце` с таймстемпом в имени файла. Рекомендуется настроить автоматический запуск этого скрипта по расписанию (например, каждый день в 2:00). Дампы хранить не менее 7 дней.

План восстановления: при сбое используется последний дамп, который восстанавливается командой `psql -U postgres -d Золотце < файл.sql`.

## 5. Защита от SQL-инъекций

В консольном приложении и в Web API все запросы к БД используют параметризованные команды (`NpgsqlCommand` с `Parameters.AddWithValue`). В EF Core миграции и запросы также защищены автоматически. Это исключает возможность внедрения вредоносного SQL-кода.

## 6. Заключение

*Данная политика описывает минимальные меры безопасности для учебного проекта. В реальной эксплуатации необходимо добавить шифрование соединений, регулярную ротацию паролей, настройку межсетевого экрана и мониторинг попыток несанкционированного доступа.*









# Мониторинг и алертинг для системы «Золотце»

## 1. Цели мониторинга

- Отслеживать работоспособность базы данных PostgreSQL, Redis и Kafka.
- Собирать метрики производительности приложения (.NET).
- Оперативно реагировать на проблемы (медленные запросы, нехватка памяти, блокировки).

## 2. Метрики PostgreSQL

- Количество активных подключений.
- Размер базы данных и таблиц.
- Время выполнения запросов (медленные запросы > 1 секунды).
- Кэш-хиты (hit ratio) – эффективность использования буферного кэша.
- Блокировки (запросы, ожидающие блокировку).

Эти метрики можно получить через системные представления `pg_stat_*` и расширение `pg_stat_statements`.

## 3. Метрики приложения (.NET)

- Время ответа API-эндпоинтов.
- Количество ошибок (HTTP 5xx).
- Использование памяти и CPU.
- Количество активных запросов в секунду (RPS).

Для сбора метрик .NET можно использовать пакет `OpenTelemetry` или `Prometheus.AspNetCore`.

## 4. Стек мониторинга

Предлагается использовать:

- **Prometheus** – сбор и хранение временных рядов метрик.
- **PostgreSQL Exporter** – экспорт метрик PostgreSQL в Prometheus.
- **Redis Exporter** – для метрик Redis.
- **Kafka Exporter** – для метрик Kafka (если запущена).
- **Grafana** – визуализация дашбордов.
- **Alertmanager** – отправка алертов (например, в Telegram или по email).

## 5. Примеры дашбордов в Grafana

- Общий дашборд «Состояние БД»: количество подключений, размер, количество блокировок.
- Дашборд «Медленные запросы»: топ-5 самых медленных запросов с планом выполнения.
- Дашборд «Производительность API»: среднее время ответа, количество запросов по эндпоинтам, ошибки.

## 6. Примеры алертов

| Условие | Действие |
|---------|----------|
| Время выполнения запроса > 5 секунд | Уведомление разработчику |
| Свободное место на диске < 10% | Срочное уведомление администратору |
| Блокировка длится > 1 минуты | Уведомление с указанием блокирующего запроса |
| Частота ошибок > 5% за 5 минут | Уведомление в чат команды |

## 7. Настройка экспортёров (для справки)

