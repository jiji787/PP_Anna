## 1. Сравнение методологий разработки ПО

| Методология | Основные принципы | Когда применять | Плюсы для моего проекта | Минусы |
|-------------|-------------------|----------------|-------------------------|--------|
| **Waterfall** | Последовательные фазы: анализ → проектирование → разработка → тестирование → внедрение. | Проекты с чёткими, неизменными требованиями. | Простота планирования, понятная документация. | Не подходит для интернет-магазина – требования меняются быстро. |
| **Agile** | Итеративная разработка, частые поставки рабочего ПО, адаптация к изменениям. | Проекты с высокой неопределённостью, стартапы. | Позволяет быстро добавлять новые функции. | Требует дисциплины команды и частого общения с заказчиком. |
| **Scrum** | Роли: Product Owner, Scrum Master, команда. Спринты, ежедневные встречи, ретроспективы. | Командная разработка с постоянным приоритетом задач. | Чёткие роли, предсказуемость. | Для одного разработчика избыточно. |
| **Kanban** | Визуализация потока задач, WIP-лимиты. Без фиксированных итераций. | Поддержка, непрерывная поставка. | Простота внедрения, гибкость. | Отсутствие временных рамок для больших функций. |

**Вывод:** Для учебного проекта «Золотце» оптимален **Agile с элементами Kanban** – веду доску задач в GitHub Projects, разбиваю работу на небольшие User Stories.

## 2. User Stories и Acceptance Criteria

### User Story 1 (покупатель)
> **Как** покупатель,  
> **я хочу** просматривать список всех товаров с возможностью сортировки по цене,  
> **чтобы** быстро найти подходящий товар.

**Acceptance Criteria:**
- При выборе пункта меню «Товары» → «Сортировка» отображаются товары, отсортированные по цене (возрастание или убывание).
- В выводе видны: название, цена, описание.
- Если товаров нет – выводится сообщение «Товаров нет».
- Сортировка не изменяет данные в БД.

### User Story 2 (менеджер)
> **Как** менеджер интернет-магазина,  
> **я хочу** изменять статус заказа («новый» → «оплачен» → «отправлен»),  
> **чтобы** отслеживать выполнение заказов и информировать покупателей.

**Acceptance Criteria:**
- В меню «Заказы» → «Изменить статус» запрашивается ID заказа.
- Выводится текущий статус (из БД).
- Менеджер вводит новый статус из списка.
- После подтверждения статус обновляется в таблице `orders`.
- При попытке изменить несуществующий заказ выводится ошибка.

### User Story 3 (администратор)
> **Как** администратор,  
> **я хочу** видеть отчёт «Сумма покупок по каждому клиенту»,  
> **чтобы** анализировать лояльность и выявлять самых активных покупателей.

**Acceptance Criteria:**
- В меню «Отчёты» → «Сумма покупок по клиентам» выводится таблица: Имя клиента, общая потраченная сумма.
- Сумма рассчитывается как `SUM(quantity * price_at_time)` из `order_items`, связанных через заказы.
- Клиенты без заказов показываются с суммой 0.
- Сортировка по убыванию суммы.

## 3. Применение Domain-Driven Design (DDD) для системы «Золотце»

### Предметная область
Интернет-магазин по продаже компьютерной техники.

### Сущности (Entity)
- **User** – покупатель (идентичность – Id). Может меняться (имя, город, email).
- **Product** – товар (идентичность – Id). Изменяемые атрибуты: цена, описание.
- **Order** – заказ (корневой агрегат). Имеет идентичность, содержит список **OrderItem**.

### Value Object
- **OrderItem** – определяет количество товара, цену на момент заказа. Не имеет собственного Id вне заказа.

### Агрегаты
- **OrderAggregate** – включает `Order` и коллекцию `OrderItems`. При удалении заказа удаляются и его позиции (каскадно).
- **UserAggregate** – пользователь и его заказы (связь один-ко-многим).

### Инварианты
- Нельзя добавить `OrderItem` с нулевым или отрицательным количеством.
- Цена в `OrderItem` фиксируется в момент добавления и не меняется при изменении цены товара.
- Нельзя изменить статус заказа с «завершён» на более ранний.

### Зачем DDD в проекте?
DDD помогает отделить бизнес-логику от технических деталей. В коде можно создать классы `Order`, `OrderItem` с методами `AddItem()`, `ChangeStatus()`, а не размазывать логику по всему меню. Это упрощает тестирование и поддержку.
